# Harness document

repository rootを基準とする。CLIの`--root <repo>`はsubcommandの前に置く。
このSkillは文書作業の手順であり、配置規約やTaskのgateを置き換えない。

## 1. 依頼と正本を確認する

ユーザーの目的、対象読者、変更範囲、指定path、作成・更新・レビューのみのどれかを確認する。既存の依頼やTaskで明らかな項目を再質問しない。レビューのみなら文書を編集しない。

AGENTS.mdが指定する配置規約を読み、指定がなければ`docs/harness/documentation-policy.md`を読む。未導入などでローカル規約がない場合は`harnessctl usage documentation`のJSON `content`で共通規約を取得する。usageは同梱版であり、ローカルの正本を読み取るものではない。ユーザーの明示指示・既存正本を保持し、同梱版で上書きしない。

対象領域のindex、既存仕様・ADR・計画を検索する。Harness導入済みなら`harnessctl knowledge index`も読むが、未登録文書を検索対象から除外しない。名前や更新日の一致だけで正本を決めない。

## 2. 配置と不足を判断する

配置規約の「配置を決める順序」と領域・形式の表を適用する。同じ問いの正本があれば更新を優先し、新規文書には既存文書で扱えない理由を残す。複数領域に必要な情報は一つの正本と参照リンクで扱う。

変更前に、対象の問い、探索した候補、主領域・形式、操作とpath、選択根拠、参照元・registryへの影響、未決事項を既存計画または変更説明へ記録する。Task schemaに独自fieldを増やさない。

網羅性の確認は、依頼されたscopeとシナリオを定め、規約の点検表で要求・正本・owner・確認方法・不足の追跡先を対応付ける。フォルダや見出しの存在を充足の根拠にしない。未確認を非該当にせず、非該当には根拠と確認者を残す。

正本の矛盾、根拠のない業務条件、owner不明、分類不能が残る項目はUNKNOWNとし、候補と影響を示して判断を確認する。確定できる独立項目は進める。配置ルールから一意に決まる通常の編集に承認を追加しない。

## 3. 範囲内で反映する

依頼が編集を含む場合、確定した配置記録に沿って変更する。未決の提案や会議メモを現行仕様へ昇格しない。owner・日付・数値・承認の根拠を捏造しない。

移動・改名・削除が依頼の達成に必要なら、参照元・registry・consumerを調べ、許可されたscopeで更新する。命名例へ揃えるだけの一括移動や空文書の生成は行わない。範囲外の不足は別work itemへ記録する。

規約本文をSkillや入口へ複製しない。配布元を持つrepositoryでは共通手順をseedにも反映し、導入先固有の判断はコピーしない。既存のphase Skillから呼ばれた場合は、そのTaskとscopeを引き継ぎ、完了後に元のphaseへ戻る。Taskのintake/preflight/verify/review/deliveryを省略したり再帰的に起動したりしない。

## 4. 確認して結果を返す

規約の裏付け・矛盾・反例の3視点で、依頼と成果物を読み合わせる。変更対象のリンク、重複する正本、未決状態、参照先と配布元の整合を確認する。

登録文書を編集した場合は内容をレビューしてからknowledgeの該当レコードを更新し、`harnessctl knowledge check`を実行する。UNKNOWNや古い内容をhash・日付の更新だけで隠さない。未導入repositoryに確認目的だけでHarnessを導入しない。policy・baseline・readinessを文書の完成扱いのために変更しない。

結果には、変更または指摘のpath、配置理由、網羅性を確認したscope、不足・未決事項、実行した検査と限界を示す。レビューのみの場合は修正先と根拠を返す。機械検査の成功を文章の意味の保証とせず、実行していないgateを通過したと報告しない。
