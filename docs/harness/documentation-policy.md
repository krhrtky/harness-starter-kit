# ドキュメントの配置と網羅性

対象は、Harnessを導入したrepositoryで文書を書く利用者・Agent・レビュー担当者。この規約は、文書の正本を一つに決め、情報の欠落を検出するために使う。

H00–H26は**知識の領域**、仕様書・ADR・Runbookなどは**文書の形式**である。領域をディレクトリで選び、形式をファイル名と本文で示す。全形式についてディレクトリを新設する必要はない。

## 1. 何を残すか、どこを正本にするか

次の順序で配置を判断する。

1. **機械が実行・検査する値か**。Task、policy、capability、knowledge登録、Evidenceは対応する`.harness/`のschemaに従う。API schema・コード・テストは既存の実装配置を正本にし、文書から参照する。JSONやコードを説明文へ複製して正本を増やさない。
2. **作業中だけ必要な情報か**。試行ログ、走り書き、一時出力はGit管理対象外の作業領域へ置く。将来の判断に必要な決定・根拠・未完了作業は、以下の文書へ要約して残す。未決仕様はUNKNOWNとして、解消担当と確認先を記す。
3. **既存文書で同じ問いに答えているか**。まず検索し、同じ読者・主題・更新契機なら既存文書を更新する。別の読者、独立した更新契機、独立して参照する主題のいずれかがあれば分割し、元の文書からリンクする。
4. **判断の経緯または一回の作業か**。重要な選択の理由は`docs/decisions/`のADR、一回の実行計画は`docs/exec-plans/`へ置く。現在有効な仕様・設計は領域文書を更新し、ADR・計画と相互参照する。
5. **継続利用する知識はどの問いに答えるか**。次節から主領域を一つ選ぶ。複数領域にまたがる場合、主たる結論を保守するownerの領域を正本にし、他領域のindexから参照する。ownerも境界も決められない場合は、候補と未決理由を計画に記録して責任者へ確認する。

既存repositoryに正本がある場合は移動を前提としない。領域indexから既存pathまたは外部正本へのリンク、owner、参照する版を示す。外部正本の内容はCLIでは検証できないため、確認日・判断に使った箇所・確認方法をローカル文書に残す。

`README.md`は入口、`AGENTS.md`はAgent向けの経路と必須行動、`ARCHITECTURE.md`は構造の地図とする。詳細をそれぞれの入口へ重複記載しない。`docs/harness/`はHarness自体の利用・運用ガイドであり、導入先アプリケーションの未分類文書置き場にはしない。

## 2. 領域ごとの配置表

各配置先は`docs/`からの相対path。例は作成条件に該当したときに残す情報で、全ファイルの作成義務ではない。

| ID・配置先 | 何を置くか・作成／更新の契機 | 隣接領域との境界 |
|---|---|---|
| H00 `product/` | 利用者、課題、成果指標、要求、非目標、優先順位。提供価値・要求が変わるとき | 業務上常に守る条件はdomain、Task単位のACの正本はTask Contract |
| H01 `domain/` | 用語、業務ルール、不変条件、業務状態遷移。概念・許容動作が変わるとき | 技術的なデータ構造はdata、通信形式はcontracts |
| H02 `architecture/` | 現行の責務分割、依存方向、設計書、システム境界。構造・接続が変わるとき | 選択理由はADR、目標像と移行戦略はevolution |
| H03 `contracts/` | API・イベント・CLIの公開契約、互換性、エラー、版管理。利用側との約束が変わるとき | schemaの正本は既存schema配置、利用側ごとの影響分析はimpact |
| H04 `data/` | データモデル、所有、整合性、保存・削除・データ移行方針。データの意味や寿命が変わるとき | アクセス制御はsecurity、障害復旧手順はreliability |
| H05 `security/` | 脅威モデル、認証・認可、秘密情報、プライバシー対策。信頼境界・扱う情報が変わるとき | AgentやCIの実行許可はauthority、法的要求・監査責任はgovernance |
| H06 `reliability/` | SLI/SLO、容量・性能予算、障害時のRunbook、バックアップ復旧。運用目標・障害対応が変わるとき | 観測手段はobservability、障害後の原因分析はfeedback |
| H07 `ux/` | 利用フロー、操作・表示仕様、アクセシビリティ、利用者向けガイド。利用体験が変わるとき | 提供価値はproduct、公開入出力の厳密な契約はcontracts |
| H08 `observability/` | ログ・メトリクス・trace設計、アラート、調査手順。観測対象・検知条件が変わるとき | 達成すべき可用性はreliability、実行ログ本体は証拠の保存先 |
| H09 `verification/` | テスト戦略、検証モデル、保証範囲・限界、再現手順。正しさの確認方法が変わるとき | 実行設定はcapability registry、品質目標・評価結果はquality |
| H10 `environment/` | 開発環境、依存関係、build手順、環境差分。再現に必要な前提が変わるとき | リリース工程はdelivery、秘密値そのものは文書に保存しない |
| H11 `delivery/` | CI/CD、配布・リリース・rollback手順、release notes。受け渡し方法・配布内容が変わるとき | サービス障害の復旧はreliability、個別実行予定はexec-plans |
| H12 `authority/` | 利用者・Agent・CIの実行権限と承認境界。実行主体・許可操作が変わるとき | 製品の認可設計はsecurity、組織の意思決定責任はgovernance |
| H13 `knowledge/` | 文書owner、更新・レビュー・失効の運用。知識を維持する方法が変わるとき | 各領域の本文はその領域。汎用メモの集積先にしない |
| H14 `exec-plans/` | Taskの実行計画、順序、依存、未決事項、完了後の残件。作業の開始・変更・完了時 | 合意したscope・ACはTask Contract、継続仕様は領域文書 |
| H15 `maintainability/` | コード構造の保守方針、変更容易性、リファクタリング基準。保守上の制約が変わるとき | 負債の一覧はquality、個別cleanupの順序はexec-plans |
| H16 `feedback/` | 障害・手戻りの事後分析、根本原因、再発防止、振り返り。失敗・学習が得られたとき | 対応中の手順はreliability、Agent評価の定量集計はevals |
| H17 `assets/` | 共有資産の提供機能、利用方法、owner・consumerの説明。再利用可能な資産を追加・変更するとき | 検索用登録値はasset catalog、採用の比較基準はreuse |
| H18 `reuse/` | reuse/extend/distinctの判断基準、配置・重複の扱い。再利用の判断方法が変わるとき | 個々の候補分析はTask、資産の使い方はassets |
| H19 `lifecycle/` | 資産の昇格・非推奨・廃止条件、移行告知。資産のサポート状態が変わるとき | システム全体の移行はevolution、個別consumer影響はimpact |
| H20 `quality/` | 品質次元、目標、評価根拠、技術負債一覧。目標・評価・負債が変わるとき | gateが読む値はquality registry、検証方法はverification |
| H21 `garden/` | 定期点検の対象・方法、整理候補と選定根拠。横断点検・整理候補の発見時 | 実行はexec-plans、負債の正本はquality、原因分析はfeedback |
| H22 `impact/` | consumer一覧の説明、変更影響、互換性・移行確認。システム境界を越える変更時 | 契約そのものはcontracts、移行戦略はevolution |
| H23 `standards/` | コーディング・レビュー・設計の共通規約と例外条件。横断的な規則が変わるとき | 機械検査のpolicy値はcontrol plane、文書配置の詳細は本規約へリンク |
| H24 `evals/` | Agentの評価シナリオ・指標・結果分析。Agentの性能・介入・手戻りを評価するとき | アプリケーションのテストはverification、個別原因分析はfeedback |
| H25 `governance/` | owner、意思決定・例外承認、監査・法令要求、コスト責任。責任分担・組織制約が変わるとき | 実行許可はauthority、対策の技術設計はsecurity等の実施領域 |
| H26 `evolution/` | current/target/transition、移行戦略、終了条件。目標構造・移行経路が変わるとき | 現行設計はarchitecture、実行順はexec-plans、廃止状態はlifecycle |

## 3. 文書形式の選択基準

命名例の`<topic>`は、検索できる主題名へ置き換える。種別と状態は本文で区別し、機械用registryに未定義fieldやstatusを追加しない。

| 形式 | 作る基準 | 配置・命名例 | 最低限残す内容 |
|---|---|---|---|
| 要求・仕様 | 期待する振る舞い、条件、境界を共有する | 主領域の`<topic>-spec.md` | 目的、対象、正常／異常条件、不変条件、非対象、確認方法 |
| Design Doc | 複数要素の責務・接続を説明しないと実装を判断できない | 主領域の`<topic>-design.md` | 背景、目標／非目標、設計、代替案、リスク、検証、移行 |
| RFC・提案 | 複数案の選択・合意がまだ必要 | 主領域の`<topic>-proposal.md` | 問題、案の比較、判断基準、決定者、未決事項。決定後はADR・仕様へのリンク |
| ADR | 後から理由を追う必要がある構造・技術・運用上の選択 | `decisions/ADR-NNN-<topic>.md` | 日付、状態、owner、背景、決定、代替案、理由、利点／負担、見直し条件 |
| Runbook | 同じ操作・復旧を繰り返し実行する | 操作対象領域の`<topic>-runbook.md` | 発動条件、権限・前提、手順、成功判定、失敗時の対応・連絡先 |
| Tutorial・How-to・Reference | 利用者が学ぶ／特定作業を行う／値を引く | 主領域の`<topic>-tutorial.md`、`<topic>-how-to.md`、`<topic>-reference.md` | 読者、前提、到達結果、実行例または厳密な参照項目。Harness利用は`harness/` |
| 実行計画 | 一回のTaskの順序・依存・進捗を管理する | `exec-plans/active/<task>.md`、完了後は`completed/` | Task参照、工程、証拠計画、未決事項、完了条件、残件。移動時は参照元を更新 |
| 調査・実験報告 | 判断に使う観測結果を再利用する | 調査対象領域の`<topic>-research.md` | 問い、出典・版・確認日、方法、結果、限界、結論、反映先 |
| 事後分析 | 障害・手戻りから再発防止へつなぐ | `feedback/<event>-postmortem.md` | 影響、時系列、原因と根拠、再発防止、担当、追跡先 |
| 会議記録 | 合意・未決事項を後から参照する必要がある | 主領域の`<date>-<topic>-meeting.md` | 目的、参加者、決定、未決事項、担当、期限、反映先。決定した仕様は正本へ戻す |
| Release notes | 利用者が版間の変更と対応を知る必要がある | `delivery/<version>-release-notes.md` | 対象版、利用者への変更、互換性、移行操作、既知制約 |

既存のファイル名はこの例に合わせるだけの改名をしない。たとえば、このrepositoryの`docs/harness/release-notes.md`はHarness配布物の既存ガイドとして継続利用し、deliveryの入口から参照できるようにする。

## 4. 最低記載事項と更新の基準

新規の継続文書には、目的・対象読者・主領域・owner・状態・最終確認日・根拠・更新契機を本文に記載する。状態は草案／現行／廃止を区別し、廃止時は後継を示す。ownerは維持責任を持つ個人またはチームとし、未定ならUNKNOWNを明示する。

領域indexは、その領域の要約、正本文書へのリンク、未決事項の追跡先を持つ。空の見出しやリンクの存在だけで知識を完成扱いにしない。根拠としてTask・ADR・テスト・schema・外部仕様の版を参照し、断定の確認方法を示す。

変更した仕様・契約・運用の正本は、その変更と同じ作業で更新する。ADRや完了計画は履歴として残し、現在の仕様と区別する。文書変更後はリンクと関連する仕様の整合性を確認する。

Gateの判断根拠として使うローカル文書は`.harness/knowledge.json`へ登録する。indexのdigestはリンク先の本文まで保証しないため、詳細文書を根拠とするならその文書も個別に登録する。レビュー後に、対応レコードのowner/status/reviewed_at/content_digestを実際の内容に合わせて更新し、`harnessctl knowledge check`で確認する。seedのUNKNOWNを文書追加だけでdocumentedへ変更しない。

この配置規約は人とAgentのレビュー基準である。現行CLIは、全Markdownの分類・本文の十分性・次節の網羅性を自動判定しない。

## 5. 現在の分類で何をカバーできるか

**H00–H26で以下の開発・運用・改善上の問いに配置先を割り当てられる。ただし、フォルダが27個あることは、プロジェクトの要求が網羅されている証拠にはならない。** 以下は本規約による分類の点検結果であり、個々のプロジェクトの記載完了を表さない。

| 点検する局面・横断事項 | 確認する情報 | 受け持つ領域 |
|---|---|---|
| 発見・要求 | 誰の何を解決し、何を達成すればよいか | product、domain、ux |
| 仕様・設計 | 振る舞い、構造、契約、データ、選択理由 | domain、architecture、contracts、data、decisions |
| 計画・実装 | 作業境界、環境、権限、再利用、実装規約 | exec-plans、environment、authority、assets、reuse、standards |
| 検証・受け渡し | 正しさ、品質、配布、利用者の移行 | verification、quality、delivery、impact |
| 運用・障害 | SLO、性能・容量、監視、復旧、事後分析 | reliability、observability、feedback |
| 進化・終了 | 目標像、移行、非推奨、廃止、データ削除 | evolution、lifecycle、impact、data、garden |
| 安全・組織制約 | 脅威、プライバシー、法令・監査、owner、承認 | security、governance、authority |
| 経済性 | 費用の上限・責任、成果との関係、容量費用 | governance、product、reliability |
| 学習・保守 | 技術負債、知識の鮮度、資産の再利用、Agent評価 | maintainability、knowledge、quality、assets、reuse、evals、feedback |

従来のindexには、RFC、Runbook、調査報告、会議記録、利用者向け説明の選択基準と、性能・コスト・法令要求の配置境界がなかった。今回は領域の追加ではなく、上記の形式表と境界の明文化で補う。

### プロジェクト固有の漏れの点検

初回導入、Task intake、公開・廃止の計画、障害の事後分析で、対象scopeについて次を行う。既存の計画文書に結果を置き、別の全社台帳を作る必要はない。

1. 利用者・運用者・consumerのシナリオを列挙する。正常系に加え、失敗・誤操作・境界値・移行・廃止を含める。
2. 各シナリオについて、上表の局面・横断事項に対する要求を確認する。
3. 各要求を次の表で追跡する。非該当は理由と確認者を残す。未確認を非該当にしない。
4. 配置不能・owner不明・確認方法不明が残れば、対象要求は未解決とする。今回のTaskに必要なUNKNOWNはpreflight前に解消する。範囲外の不足は別work itemへ記録する。

| 要求／問い | 該当・非該当と根拠 | 正本path・節 | owner | 状態（確認済／不足／未確認） | 確認方法・証拠 | 不足の追跡先 |
|---|---|---|---|---|---|---|
| 対象scopeの具体的な要求を1行ずつ記載 | 非該当には確認者も記載 | 主領域の正本 | 維持担当 | 文書の有無だけで確認済にしない | test／review／参照仕様の版 | Task等 |

網羅性を「対象scope内で確認した」と言える条件は、列挙したシナリオの全要求に正本・owner・確認方法があり、非該当に根拠があり、不足・未確認が0件であること。未知の要求が存在しないという証明にはしない。

### 分類を増やす条件

既存領域へ置くと責任者または更新契機が継続的に混在し、リンクや主題別の分割でも解消できない場合に、独立した分類を検討する。具体的な配置不能文書、既存分類で扱えない理由、owner、既存文書の移行先をADRに記録する。

ディレクトリの追加とHarness interfaceの追加は別の変更である。H00–H26はschemaで固定されているため、独自のH27をregistryへ記入しない。まず既存interfaceに属する主題別配置を検討し、新interfaceが必要ならschema・seed・検査・移行・consumerを含む別Taskで扱う。

## 6. 配置判断の例

- **注文キャンセル**: 利用者の目的は`product/`、出荷後は不可という不変条件は`domain/`、APIの入力とエラーは`contracts/`。今回のscope・ACはTask Contract、実装順は`exec-plans/active/`へ置く。
- **DB採用と移行**: 比較・採用理由はADR、現在の接続構造は`architecture/`、データ変換仕様は`data/`、移行戦略は`evolution/`、一回の移行工程は`exec-plans/active/`。同じ説明を5か所へコピーしない。
- **本番障害**: 即時復旧は`reliability/`のRunbook、調査クエリは`observability/`、確定した原因・再発防止は`feedback/`。ログは実行証拠の保存先を参照する。
- **個人情報の保持期間**: 法令・契約要求と確認責任は`governance/`、保持・削除仕様は`data/`、アクセス制御と脅威対策は`security/`。未確認の法的条件を推測で仕様へ埋めない。

## 7. AI Agentの実行契約

文書の作成・更新・移動・削除に着手する前に、この節と対象領域のindex・既存正本を読む。ユーザーが示した目的・配置先・変更範囲を保持する。一般規約を理由に明示された指示を置き換えない。指示と既存契約の衝突があれば、衝突する変更を行う前に具体的な差分と影響を提示する。

### 配置を決める順序

上から順に適用し、決まった配置を下位の命名例で変更しない。

1. ユーザーが今回明示した配置・範囲を採用する。
2. 既存の正本指定、knowledge登録、領域indexを調べ、同じ問いの正本を更新する。単に新しい日付であることを正本の根拠にしない。
3. 正本がなければ、機械用契約／一時情報／ADR／実行計画を第1節の順に判定する。
4. 継続文書は第2節の「答える問い」と境界で主領域を一つ決め、第3節で形式を選ぶ。キーワード一致だけで決めない。
5. 複数の問いが独立している場合は主題別に分ける。一つの問いの候補が複数残る場合は主たる結論のownerで決める。
6. 正本同士の矛盾、owner不明、既存分類に該当しない要求が残れば、その項目をUNKNOWNにし、候補path・選択による影響・必要な判断を利用者に確認する。独立して確定できる項目は進める。

既存の明確な根拠から決まる通常の配置について、毎回の承認を求めない。UNKNOWNを解消するための調査と、新たな業務判断の決定を区別する。

### 書く前に残す配置記録

既存のTask計画、または文書だけの変更なら変更説明に次の表を残す。検討経過を仕様本文やコードコメントへ混ぜない。Task schemaへ独自fieldを追加しない。

| 対象の問い | 検索した正本・候補 | 主領域／形式 | 操作とpath | 選択根拠 | 参照元・registryへの影響 | 未決事項 |
|---|---|---|---|---|---|---|
| 1つの問いを記載 | pathと該当節。見つからない場合は検索範囲 | Hxx／仕様等 | 更新・新規・参照・移動・削除 | 上記の適用規則、既存文書を使える／使えない理由 | 更新対象を列挙 | なければ「なし」 |

### 作成・更新時の制約

- 新しい文書を作る前に、同じ問いの既存文書を更新できない理由を記録する。章追加で足りる場合はファイルを増やさない。
- 複数領域から必要な情報は、一つの正本と参照リンクで扱う。正本が矛盾していたら、Agentが独断で片方を削除・統合しない。
- 提案・会議メモ・推測・UNKNOWNを現行仕様として記載しない。決定根拠がないowner、承認、日付、数値、非該当理由を生成しない。
- 分類の見た目を揃えるだけの一括移動・改名・削除、全形式の空文書生成を行わない。移動・削除が目的に必要なら、参照元・registry・consumerの影響を先に列挙し、許可されたscopeで更新する。
- `.harness/`のschema、policy、baseline、capability、readinessを、文書を完成扱いにするために変更しない。規約変更が必要なら通常の別Taskとレビューへ分ける。
- seedを持つ配布repositoryで共通ルールを変える場合は配布元にも反映し、導入先固有の判断や履歴をseedへコピーしない。このrepositoryでは`src/harnessctl/resources/seed/`が配布元に当たる。

### 完了前のレビュー

| 視点 | 合格条件 | 不合格例 |
|---|---|---|
| 裏付け | 依頼の各要求に、配置先・選択根拠・確認方法がある | フォルダ一覧を追加しただけで「網羅」とする |
| 矛盾 | ユーザーの意図・既存正本・schemaと整合し、重複する正本がない | 提案書にしかない条件を現行仕様へ昇格する |
| 反例 | 複数領域、正本なし、正本衝突、非該当、移動後の参照について適用結果を説明できる | owner不明なのにpathを推測し、空文書で埋める |

変更した文書のローカルリンク、登録文書のdigest・鮮度、配布seedとの共通部分も確認する。文章レビューと機械検査は別々に結果を示し、実行していないgateの通過を報告しない。

### 判断例による確認

| 入力 | Agentが選ぶ動作 | 行ってはいけない動作 |
|---|---|---|
| `domain/orders.md`がキャンセル規則の既存正本 | 同じ問いなら既存ファイルを更新 | 命名例に合わせ`cancel-spec.md`へ複製 |
| ユーザーが既存`design/payment.md`の更新を指定 | 指定pathを保持し、必要な領域indexから参照 | 一般表だけを理由に`docs/architecture/`へ移動 |
| 会議で保持期間の候補が2つ出たが未決 | 候補と決定者を記録し、確認を求める | 一方を選んでdataの現行仕様にする |
| API変更に伴うconsumer移行 | 契約はcontracts、利用側の影響はimpact、実行順はexec-plansへ分けて相互参照 | 同じAPI仕様を3か所へコピー |
| 機能に個人情報が関係するか未確認 | 未確認として担当・調査先を記録 | securityを非該当として網羅性を合格扱い |
| 独自の分類が必要だがH27は未定義 | 既存interface配下での配置を検討し、無理なら別Taskへ | schemaやregistryへH27をその場で追加 |
